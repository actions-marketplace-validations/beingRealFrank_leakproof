Is the Supabase anon key safe to expose in my frontend?

Short answer: yes, the anon key is public by design, and it is only safe if Row Level Security is on for every table. Anyone can read the key from your site's JavaScript. What it can do is decided by your RLS policies, not by keeping the key secret. The service_role key is different: it ignores RLS and must never reach the browser.

Check 1: tables with RLS off

select schemaname, tablename
from pg_tables
where schemaname = 'public' and rowsecurity = false;

Every row returned is a table that the anon key can read and write through the REST API, whatever your UI shows. Fix:

alter table public.<table> enable row level security;

Check 2: policies that let everyone in

select tablename, policyname, cmd, roles, qual, with_check
from pg_policies
where schemaname = 'public'
  and (qual = 'true' or with_check = 'true');

using (true) on a select policy means "anyone can read every row", which is fine for a product catalog and a leak for anything per-user.

Check 3: prove it from the outside

curl "https://<project>.supabase.co/rest/v1/<table>?select=*&limit=5" \
  -H "apikey: <anon key>"

Signed-out, this should return [] or an error for any private table.

Check 4: the service_role key

Search your code for SERVICE_ROLE and check none of it is in a 'use client' file, a NEXT_PUBLIC_ / VITE_ variable, or committed to git. If it ever was, rotate it.
