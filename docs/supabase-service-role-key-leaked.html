Supabase service_role key leaked: what to do

The service_role key ignores Row Level Security entirely, so whoever holds it can read and write your whole database. If it was ever in the browser bundle or in git, treat it as compromised.

1. Find where it is

Search your code for SERVICE_ROLE and check none of it is in a 'use client' file, a NEXT_PUBLIC_ / VITE_ variable, or committed to git.

grep -rnE "(NEXT_PUBLIC|VITE|EXPO_PUBLIC|REACT_APP)_[A-Z0-9_]*(SECRET|SERVICE_ROLE|PRIVATE|OPENAI|ANTHROPIC|DATABASE_URL|WEBHOOK)" \
  --exclude-dir=node_modules --exclude-dir=.git .

2. Check what actually shipped

Source can look clean while an old build still leaks. Build, then search the output:

npm run build
grep -rnoE "sk_live_[A-Za-z0-9]{10,}|sk-(proj-)?[A-Za-z0-9_-]{20,}|sk-ant-[A-Za-z0-9_-]{20,}|sb_secret_[A-Za-z0-9_-]{10,}" .next/static dist build 2>/dev/null | head

Supabase's older keys are JWTs, so the word service_role is encoded inside them. To check one you find in the bundle, decode its middle part: echo '<key>' | cut -d. -f2 | base64 -d 2>/dev/null. It must say "role":"anon".

3. Rotate it

Removing a key from the code doesn't un-leak it: it's in old deployments, browser caches and git history. Create a new key in the provider's dashboard, deploy with it, then delete the old one.

4. Keep it on the server

Vite apps (Lovable, Bolt) have no server of their own: put the call in a Supabase Edge Function, read the key there with Deno.env.get('OPENAI_API_KEY'), and set it with supabase secrets set OPENAI_API_KEY=…. Use the user's own Supabase client in server code (so RLS applies), or add .eq('user_id', user.id) to every query.

5. Keep .env out of git

git ls-files | grep -E '(^|/)\.env'

This should print nothing, or only .env.example. If it prints more, add .env* and !.env.example to .gitignore, run git rm --cached on the file, and rotate every value in it.
