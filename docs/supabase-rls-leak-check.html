Supabase RLS leak check

Your Supabase anon key is in your frontend, so Row Level Security is the only thing between it and your users' data. This check reads your migrations and flags the two mistakes AI builders leave behind most: tables that never enable RLS, and policies that let everyone in.

Run the free scanner

One command, runs locally, nothing is uploaded except an optional dependency lookup:

npx github:beingRealFrank/leakproof

Add --offline to skip that lookup. It is also a GitHub Action that runs on every pull request.

What it reports

Output on a small sample project with one table missing RLS and one allow-all policy:

CRITICAL LP004 Supabase/Postgres table without Row Level Security
         supabase/migrations/001.sql:1  create table todos
         Fix: alter table public.todos enable row level security;  then add policies, e.g.
         create policy "own rows" on public.todos for all using (auth.uid() = user_id) with check (auth.uid() = user_id);

CRITICAL LP005 Row Level Security policy that allows everyone
         supabase/migrations/001.sql:4  create policy "everyone" on public.profiles for all using (true);
         Fix: Replace true with an ownership check, e.g. using (auth.uid() = user_id) with check (auth.uid() = user_id).

Check your live database too

A scanner only sees your repo. Run these in the Supabase SQL editor to see what is actually deployed:

select schemaname, tablename
from pg_tables
where schemaname = 'public' and rowsecurity = false;
select tablename, policyname, cmd, roles, qual, with_check
from pg_policies
where schemaname = 'public'
  and (qual = 'true' or with_check = 'true');
